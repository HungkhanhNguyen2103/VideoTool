# Module: project

**Purpose:** Project CRUD and the scene model (scenes are embedded in the project document); optimistic locking via version.
**Owns collection(s):** projects
**May import (via their index.ts only):** none
**Public API:** only what `index.ts` exports. Nothing else in this module may be imported from outside.

## Invariants
- Scenes have an additive `active` flag defaulting to `true` in both the contract and Mongo document schemas, so legacy documents remain active. `contracts/scene-active.ts` is the shared definition; toggling through `setProjectSceneActive` uses a version-guarded atomic write, preserves every other scene field, and recomputes chapter duration summaries from active scenes. Idempotent toggles do not increment the version. Project-list scene counts and durations also include active scenes only.
- `_id` is a ULID string, never an ObjectId.
- `titleSearch` is always `normalizeTitle(title)` (title-search.ts): NFD, strip diacritics, `đ`->`d`, lowercase. Kept in sync on create and duplicate; if `title` is ever updated in place, `titleSearch` must be recomputed in the same write.
- `status` starts at `draft` on create. `duplicateProject` clears scene asset references because files are not copied, maps `rendered` -> `assets` (a copy has no video file), and copies every other status as-is.
- `scenesCount`/`durationSec` in `ProjectSummary` are never stored; they are computed from `scenes` at query time (`repo.listProjectSummaries`), and are `null` when `scenes` is empty.
- `version` starts at 1 on create and on duplicate (a duplicate is a new document, not a revision), then increments on every scene/chapter mutation. Scene asset metadata defaults to `assetType: 'image'` and `assetFileId: null` when legacy documents are read.
- Scene asset mutations are public service APIs: `patchProjectScene` targets one scene, `setProjectScenesAssetType` updates all scenes, and `applySceneAssets` applies deduplicated file references in one atomic update.
- `applyEmptySceneVisualPrompts` keeps its `ProjectDetail` return contract and delegates to `applyEmptySceneVisualPromptsWithResult`. The companion is the sole atomic writer for AI visual prompts: it validates scene IDs, keeps the last submitted prompt per ID, and updates only scenes whose `visualPrompt` is still empty. A single `findOneAndUpdate` returns the pre-image used to identify exactly which scene IDs changed. The top-level empty-target predicate and per-target array filters let concurrent manual edits win; a batch with no eligible target returns an empty ID list and leaves `version` unchanged. The existing scene schema already stores `visualPrompt`, so no migration is needed.
- Scene durations accept non-negative seconds with at most two decimal places; legacy integer values remain valid. Scene schema defaults include `audioFileId: null`, `voiceoverDurationSec: null` (the raw probed voiceover length), `sfxPrompt: ''`, and `sfxFileId: null`. Project `sceneTailSec` defaults to `DEFAULT_SCENE_TAIL_SEC` (0.2 seconds) and `sfxVolume` defaults to 0.5 for legacy reads; both settings are copied on duplication. Other defaults include `renderEngine: 'ffmpeg'`, `keywordPopupsEnabled: true`, `voiceoverVoice: 'Truc Ly'`, `renderFileId: null`, `draftRenderFileId: null`, `bgmMood: ''`, `bgmFileId: null`, and `logoFileId: null`.
- Project `voiceSpeed` defaults to 1.0 for legacy reads and accepts 0.8 through 1.3 in 0.05 steps. A scene's generated `voiceoverInput` records the effective voice, speed, and narration hash; missing or mismatched input is stale. Narration/audio edits clear that input, duplicate projects clear it with audio references, and voiceover attachment is guarded by the captured project version.
- Duplicating a project never carries `assetFileId`, `audioFileId`, or `sfxFileId` scene references, and clears project `bgmFileId`/`logoFileId`/`renderFileId`/`draftRenderFileId`; prompts, mood, and render settings remain. File metadata and disk files remain owned by the source project.
- SEO is an additive embedded package with schema defaults for legacy project reads. `patchProjectSeo` and `applyGeneratedSeoSections` are the only project-owned SEO writers; section updates increment `version` once, and duplicate projects retain SEO text/ideas while clearing `seo.thumbnail.fileId` because binary files are not copied.
- `setProjectBgm` atomically updates `bgmMood` and `bgmFileId`; `setProjectRenderFile` atomically updates `renderFileId` and `status: 'rendered'`. Both increment `version` once.
- `setProjectLogo` atomically updates `logoFileId` and increments `version` once; video owns logo file replacement/removal while project remains the only writer of the reference.
- `setProjectRenderEngine` atomically updates the engine selection and increments `version` once; consumers call it through the public module index.
- `setProjectKeywordPopups` atomically updates the Remotion keyword overlay setting and increments `version` once; duplication preserves it.
- `setProjectSceneDurations` applies measured voiceover lengths and frame-independent scene seconds only when the captured project version and each scene's audio file ID still match; it updates chapter duration summaries and increments `version` once. It does not alter word timings because the audio is unchanged. Narration edits and audio resets clear the raw voiceover duration; duplicate projects clear it with the audio references.
- `patchProjectScene` chapter duration summaries and `setProjectSceneDurations` chapter summaries sum active scenes only. A duration recompute batch skips inactive scenes and reports their count; toggling a scene does not clear any stored media, timings, prompts, or analysis data.
- Duplicate projects preserve each scene's `active` value, including `false`, while retaining the established reset of all scene media, voiceover, timing, name, and popup references because binary files are not copied.
- `setProjectSceneTailSec` persists the 0–2-second, two-decimal project tail setting. Changing it does not silently rewrite existing scene durations; the video module's explicit recompute action does that from stored WAVs.
- `setProjectSfxVolume` persists a project SFX gain from 0.00 through 1.00 in hundredths. It is applied after render-time normalization in both render engines.
- Scene `nameCandidates` are project-owned persisted analysis records. A narration edit clears `audioFileId` and `wordTimings` but retains the previous candidate record; Studio reports it as `đã cũ`, and the scene's read-only popup line is `—` until new audio and alignment exist. With new aligned audio, the old candidate remains stale and selection falls back to rules until analysis refreshes it (`có kết quả mới`). Per-scene voiceover regeneration also retains the old record as stale. Duplicating a project or bulk-replacing scenes with `audioFileId: null` clears the record (`chưa phân tích`, with rule-based selection). Fresh candidate batches, including valid empty candidate lists, are written only through `setProjectSceneNameCandidates`, guarded by the captured narration and audio ID. Explicit re-analysis may change the candidate choice or metadata in ambiguous ties; Remotion continues to consume the persisted record unchanged between analysis runs, so renders remain stable between those runs.
- Task 97 adds additive `popupDensity` (`low` by default) and a per-scene `popupPlan` beside the legacy `nameCandidates`. Popup plans carry the narration hash, audio snapshot, provider/model/backend/density, generated timestamp, every AI verdict, validated kept/dropped popups, and safety-net reasons. `setProjectScenePopupPlans` is the guarded project-owned writer; it increments `version` once and ignores writes after a narration/audio race. Duplicate projects clear popup plans with their cleared audio. Legacy `nameCandidates` remains readable and writable for its old routes, but video popup selection never reads it.
- `setProjectPopupDensity` is the project-owned mutation behind `PATCH /api/project/:id/popup-density`; popup analysis requests may use the persisted density or an explicit per-job override without changing provider/model settings.
- `aiModel` is optional on legacy project documents; the shared AI registry supplies the provider default at client construction without a data migration. New-project and provider-update requests validate that the model belongs to the selected provider. `setProjectAiProvider` atomically updates the provider/model pair and increments `version` once; switching providers chooses that provider's default, while keeping the current provider preserves a valid selection. Duplicates preserve the model.
- `setSeoThumbnailFile` atomically updates the thumbnail file pointer and increments `version` once; the SEO module owns file replacement/deletion while calling this public project mutation.
- `replaceProjectScript` atomically replaces generated chapters, open loops, motif, optional status, and optional history snapshot in one versioned project update.
- Script continuity fields are additive and default safely for legacy reads: project `coreQuestion`/`openingHook` use `''`; chapter `chapterSummary` uses `null`, `avoidRepeating`/`persistentFacts` use `[]`, and `reviewStatus` uses `'clean'`.
- Delete is a hard delete (`repo.deleteProjectById`); the app-level delete route removes referenced final, draft render, logo, and SEO thumbnail files through the file-store hook before deleting the project.

## Flow
- `POST /api/project` -> `routes.ts` parses the body with `CreateProjectRequestSchema` (validation + Vietnamese messages live in `contracts/project.ts`, copied from `docs/prototypes/khoi-tao-du-an/app.js`) -> `service.createProject` builds the `ProjectDoc` and inserts it -> `service.toDetail` shapes the response (`ProjectDetail`, dates as ISO strings).
- `GET /api/project` -> `ListProjectsQuerySchema` (optional `q`, `status`) -> `repo.listProjectSummaries` runs an aggregation: `$match` (status + accent-insensitive `titleSearch` regex, query escaped by `escapeRegex`), `$sort` by `updatedAt desc`, `$limit` 200, `$project` computing `scenesCount`/`durationSec` (duration sum rounded to two decimal places).
- `GET /api/project/:id` -> `service.getProject` -> `NotFound` (404) if missing.
- `POST /api/project/:id/duplicate` -> `service.duplicateProject`: loads the source doc, clones it under a new id/title/timestamps, clears scene asset references, resets `version`, and applies the `rendered -> assets` status rule.
- `DELETE /api/project/:id` -> `service.deleteProject` -> `NotFound` (404) if nothing was deleted.

## Known pitfalls
- `contracts/project.ts` validates the whole payload in one `superRefine` so each field surfaces exactly one Vietnamese message (matching the prototype's `validate()`), instead of zod's default per-check messages; don't add plain `.min()/.max()` messages on those fields; they should be silently added to the same `superRefine`.
- `escapeRegex` is required on every user-supplied `q` before building the `$regex` filter; skipping it would let a search string break out of the intended match (ReDoS/incorrect matches).
- No automated tests were written for this module in Phase 1 (by explicit request); it has been checked with `npm run typecheck`, `npm run lint`, and throwaway scripts for `CreateProjectRequestSchema` and `title-search.ts`. The live MongoDB endpoints, health check, browser CRUD flow, reload persistence, search/filter behavior, and delete fallback were manually verified on Windows on 2026-09-22.
- Task 6/6 final integration audit confirms project-owned chapter/script/scene persistence remains compatible with the Tasks 1-5 continuity, manual import, finalization, regeneration, legacy-default, and read-only Final QA flows; no project-module ownership or scene-shape changes were required.
