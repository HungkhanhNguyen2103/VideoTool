# Architectural design — approved, with two precisions before writing the spec

Checked the two load-bearing claims directly against the real schemas before approving, since they decide whether "no migration" actually holds and where a new route belongs.

- **Additive-fields-with-defaults on `ChapterDoc` is sound.** I read the current `ChapterDocSchema` in `src/contracts/script.ts` (`id, no, title, paragraphs, status, scenesCount, durationSec` — the last two already `.nullable()`), and this project has already shipped exactly this pattern once before (AGENTS.md's Status section records "legacy project reads apply defaults for new script fields" from an earlier phase). So `role`/`beat`/`targetWords`/`endsOnTension` as new fields with Zod `.default(...)` values, no migration script, is a proven approach here, not a new risk. Same reasoning applies to `openLoops`/`motif` as new additive `ProjectDoc` fields with `motif` defaulting to `null`.
- **Overall shape is right**: two-stage job unconditionally (no threshold), 5-act weighting for `documentary`/`hubris-trap` only with a flatter shape for `explainer`, `endsOnTension` true-except-last, 80%-of-target one-retry-then-accept, review-UI and `finalizeScript()` both switching to word-count-derived duration (the reasonable-minimum-for-very-short-narration safeguard in `finalizeScript()` is a good addition I didn't ask for but should keep), `regenerateChapter` left behaviorally untouched aside from the four new prompt inputs, manual mode staying synchronous/single-combined-prompt/outside the job queue/no raw-prompt persistence/preserving invalid pasted text for correction, and the `hubris-trap` preset carrying all four motif fields. Approved as described.

Two things to pin down explicitly in the spec, not leave implicit:

1. **Route ownership for `ai-provider`.** I checked where the render-engine precedent you're following actually lives: `router.patch('/:id/render-engine', ...)` is in `src/server/modules/video/routes.ts`, not `project/routes.ts` — the mutation (`setProjectRenderEngine`) lives in `project/service.ts`, but the route is owned by the module that's the actual *consumer* of the field (video, since render engine is a video-rendering concern). `aiProvider` today is consumed only by `script` (`generateScript`, `regenerateChapter`). So the same precedent puts the new `PATCH .../ai-provider` route in `script/routes.ts`, calling a new `setProjectAiProvider` exported from `project/index.ts` — not in `project`'s own router. Say this explicitly in the spec rather than "project-owned PATCH," since that phrase reads as project owning the route, and the precedent you're citing actually says the opposite.
2. **Three response shapes need three explicit names, not one overloaded parser.** There are now three genuinely different JSON shapes: the outline call's response (chapters with `role`/`beat`/`targetWords`/`endsOnTension`, plus `openLoops`/`motif`), the per-chapter expansion call's response (`paragraphs` + `styleNote` for one chapter), and manual mode's single combined response (everything — outline metadata *and* every chapter's full paragraphs — in one document, since manual mode isn't split into two calls). Calling the manual-mode parser `parseGeneratedChapters` reads as if it's the same schema as one of the automatic-mode calls, but it isn't the same shape as either. Give each of these three shapes its own schema/parser name in the spec, and state precisely how manual mode's combined schema relates to the other two (a superset built by combining both, or its own independent definition) — "shares the same canonical save path" should mean the persistence step (`replaceProjectChapters` etc.) is shared, not that the same Zod schema validates all three response shapes.

Everything else is approved as proposed. Write the dated design spec with these two points made explicit, commit only that, and stop for review before an implementation plan — same flow as every prior phase.

One process note, not a design point: for the implementation phase, work directly on the `main` branch in the real checkout — no isolated worktree, no separate implementer/reviewer subagents. Code, test, self-review the diff, and commit incrementally on `main`, same as every phase before the last one. This is cheaper and doesn't need a merge-back step afterward.
