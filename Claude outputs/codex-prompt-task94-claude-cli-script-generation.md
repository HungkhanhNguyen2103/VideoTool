## Goal
Task 93 added a "Claude CLI" regeneration mode (runner `modules/script/cli-runner.ts`, job `cli-regenerate-handler.ts`, availability route `GET /api/script/cli-status`, config `CLAUDE_CLI_*`, run folders `data/files/<projectId>/cli-runs/<runId>/`). Today that pipeline only runs through the API (`generateScript` in `service.ts`, job `handleGenerateScript`) or manual paste. ## Core design constraint: do NOT fork the pipeline
`generateScript` already contains all Task 91 logic (outline validation, JSON repair, source-fact coverage, budgets, length retries, transient-failure backoff, resume, history, cancellation). Today it takes its model from `getAiClient(project.aiProvider, project.aiModel)` and talks to it through `aiClient.chat(messages, { json, maxTokens, … })` (see the JSON chat helper around `service.ts:82–165` and the chapter loop around `:380–440`). The CLI mode must reuse that code path by injecting a **different chat backend**, not by copying it:

1. Extract/define a small backend interface (e.g. `ScriptChatBackend` = the subset of `AiClient` the pipeline uses: chat with messages + options, returning `{ text, truncated }`, plus a `label` for provider/model metadata). The API backend is the existing client unchanged; behaviour with `aiProvider`/`aiModel` must stay byte-for-byte identical for automatic mode (existing tests are the proof — do not weaken them).
2. Implement a `ClaudeCliChatBackend` on top of Task 93's `runClaudeCli`: each call serializes the messages exactly like the manual prompt format (`SYSTEM\n…\n\nUSER\n…` — reuse the existing formatter, do not invent a new one), runs the CLI, reads the captured output file, returns the text. `truncated` is `false` unless you can detect truncation reliably from the CLI (check `claude --help` / observed behaviour; if the CLI has no output-token control, say so in `MODULE.md` and rely on parse failure + the existing length checks). Honor `AbortSignal`/cancellation by killing the child process tree, exactly as in Task 93.
3. Every backend call writes its own run folder (`prompt.md`, `output.txt`, `meta.json`) under `cli-runs/<runId>/`, with a stable step label in `meta.json` (`outline`, `outline-repair`, `chapter-3`, `chapter-3-length-retry-1`, …) so a failed run can be diagnosed afterwards. Keep Task 93's retention rule but make it count runs per project sensibly (a 7-chapter script can create 20+ folders; raise the cap or prune by age, and say what you chose).
4. Job plumbing: add a `backend: 'api' | 'cli'` (default `'api'`) to the generate-script job payload and route body (`contracts/script.ts`, zod; old clients and queued jobs without it keep working). Resume (`resume: true`) must work in CLI mode and may even switch backend between runs (a script started via API can be resumed via CLI and vice versa) — verify and test this.
5. Process-level safety (already solved in Task 93, reuse): stdin prompt, `shell:false`, empty temp cwd, tools disabled, no session persistence, size cap, timeout, never log prompt/output bodies at info level. A single CLI call here is much larger than a regeneration (outline prompt carries brief + references; chapter prompts carry memory) — confirm the existing timeout/size defaults are enough and adjust only with evidence from a real run.
6. Failure semantics stay as Task 91 defined them: transient/provider-like failures retry per the existing rules; **auth/rate-limit/not-installed/timeouts from the CLI are NOT transient-retried** (same decision as Task 93) — they stop the run, keep the saved outline and completed chapters, and leave the project resumable via "Viết tiếp từ chương k". Malformed JSON gets the same single repair attempt as API mode.
