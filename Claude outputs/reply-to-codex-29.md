# ReviewScriptPage: chapter-list + sidebar don't match the prototype — bigger than the stepper fix, needs a short task list

The user compared a live screenshot against `docs/prototypes/duyet-tai-tao/` (already committed, confirmed byte-identical to the reference they sent) and circled the chapter-list + right-sidebar area. I read both `ReviewScriptPage.tsx` (post-`701a5de`) and the full prototype (`index.html`, `app.js`, `styles.css`) side by side. This isn't a styling miss like the stepper — the interaction model itself diverged from the design during Phase 3 implementation. Below is the complete gap list, plus one real behavioral bug I found while comparing (not just cosmetic).

## Real bug, not just a design gap: "Duyệt tất cả" doesn't do what it says

Current code: the toolbar's "Duyệt tất cả" button only appears when `selectedChapters.length > 0` and calls `approveSelected()`, which approves only the checked chapters. The label says "approve all" but the behavior is "approve selected." In the prototype, `els.approveAll` is a single always-visible button that approves **every** non-generating chapter regardless of selection (`chapters.forEach((c) => { if (c.status !== 'generating') c.status = 'approved'; })`), and selection-scoped approval isn't a separate feature at all — selection in the prototype only drives the regen sidebar. This needs a decision, not just a copy-paste: either (a) match the prototype exactly — "Duyệt tất cả" approves literally everything, always visible, and drop the selection-scoped approve entirely — or (b) keep a selection-scoped approve action but rename it so it doesn't claim "tất cả." I'd lean (a) for fidelity to the approved design, but flagging both since it changes behavior a user could be relying on.

## Structural gaps (layout + interaction model)

1. **No two-column layout.** The prototype's `.review-grid` is chapter list (flex, grows) + a fixed `340px` `.side` column containing two *persistent* panels: "Yêu cầu tái tạo" and "Lịch sử phiên bản." The current page is single-column; regen is an inline per-card popup, and history is a toggle-triggered overlay (`historyOpen` aside), not a persistent panel.

2. **Regen is per-card in the current code, but the design is select-then-compose-once.** In the prototype, the instruction text + level (Nhẹ/Vừa/Viết lại) live in exactly one place — the sidebar panel — and apply to whichever chapters are currently checked via `regenOptions()`. Clicking a single chapter's own "Tái tạo" button (`data-action="regen"`) reuses that *same* shared instruction/level, targeting just that one chapter (`regenerate([c.id], regenOptions())`). The current implementation instead pops open a separate, per-card instruction+level form (`regenDraft`) for every chapter, and has no persistent shared panel at all. Recommend porting the prototype's model: one "Yêu cầu tái tạo" panel bound to `selectedChapters`, with a chip showing "Áp dụng cho N chương đã chọn" (`chip--amber`, exact text prototype uses in `els.selectedCount`), textarea, the existing 3-way level control, and a button labeled `Tái tạo N chương đã chọn`. A chapter's own "Tái tạo" button still exists per-card but reads the same shared instruction/level state and targets just that chapter.

3. **History is a passive, always-visible side panel, not a toggle.** Port `.side`'s second panel: list every version with time and a note (`snapshot`/`pushVersion` pattern — this part of your data model already exists via `getChapterHistory`), current version gets a green "Hiện tại" badge, others get a "Khôi phục" button. No open/close state needed — it's just always rendered in the sidebar. (Confirm your `ChapterSnapshot` API already carries enough for "current vs not" — if not, the item most recently pushed can stand in for "current" until a real flag exists.)

4. **Chapter cards don't collapse.** Prototype: each card has a `chapter__toggle` button wrapping the no/title/meta, a chevron that rotates on `aria-expanded`, and the body (`chapter__body`) is `hidden` unless `expanded` or `editing`. Current cards always render full body. Worth porting for parity, though if you'd rather keep everything always-expanded as a deliberate simplification, say so explicitly rather than silently dropping it — it's a real UX difference on a 5+ chapter script.

5. **Missing header/summary stats.** Prototype shows `{total} chương • {totalScenes} cảnh • {totalSeconds}s` above the chapter list, and a `chip--meta` with the same scene/second totals in the page header next to the project title. Current code only shows `{chapters.length} chương`. Caveat: this needs `scenesCount`/`durationSec` populated per chapter before finalize, which your screenshot shows as `— cảnh · —s` placeholders right now (i.e. not computed yet at the draft stage) — confirm whether that's expected to stay empty until "Chốt & chia cảnh," in which case the summary line should just omit scenes/seconds until then rather than showing `NaN` or `— cảnh`, or whether AI generation should be estimating per-chapter scene/duration counts up front like the prototype's mock data does. This is a real question, not something to guess at — answer it in your response before implementing this one.

6. **Action buttons: no icons, wrong color for "approved," flag isn't a toggle.**
   - Prototype prefixes each action with an icon (`flag`, `edit`, `refresh`, `check`) via the shared sprite; current buttons are text-only. `Button` already accepts arbitrary children (`ButtonHTMLAttributes` → `DOMAttributes.children`) and `.btn` already has `gap: 8px`, so `<Button><Icon name="edit" />Sửa</Button>` works with zero component changes — just wire it up per action.
   - The approved-state button uses `variant="amber"` in current code; prototype uses `.btn--green` for the approved state specifically (amber is reserved for the *active/selected* look, e.g. the level segmented control). `Button.tsx`'s variant union (`ghost | amber | indigoline | red`) has no `green` — add one: `.green { background: var(--green-bg); border-color: var(--green-bd); color: var(--green); font-weight: 600; }` (values already in `tokens.css`, this is a straight port of the prototype's `.btn--green`).
   - "Cần sửa" is a toggle in the prototype (`data-action="flag"`, icon-only button, `aria-pressed`, flips `needs-fix` ↔ `pending`) rendered as a small icon button, not a full-width text button. Current "Cần sửa" always sets `needs-fix` with no way to un-flag except by approving. Port the toggle behavior and the icon-only compact style (`btn--icon`, 34px square, amber background when `is-on`).
   - "Duyệt/Đã duyệt" toggles too in the prototype (click again to un-approve) — current only sets `approved`, no toggle back.

## What's fine as-is / don't change

- The streamed regen preview (`regen.preview` filling in live via SSE) is a real improvement over the prototype's fake `setInterval` percentage simulation — the prototype has no equivalent because it has no real backend. Keep the streaming preview; just make sure it still renders correctly once the shared sidebar panel replaces the per-card popup (the preview state can stay scoped to "whichever chapter is currently regenerating," same as today).
- Status badge tones (`approved`→green, `needs-fix`→amber, `generating`→indigo, `pending`→muted) already match `STATUS` in the prototype exactly. No change needed there.

## Suggested approach

This is bigger than a same-day patch — it's finishing an interaction model that got simplified during Phase 3 implementation. No full design/plan doc needed (the prototype *is* the design doc, already in the repo), but treat it as a short task list rather than one commit:
1. Add `Button`'s `green` variant + an icon-only compact variant (or a small `IconButton`, your call) matching `.btn--icon`.
2. Rebuild the chapter card: collapsible body, icon-adorned actions, toggle semantics for flag/approve.
3. Replace the per-card regen popup with the shared sidebar "Yêu cầu tái tạo" panel bound to selection.
4. Replace the history toggle-aside with a persistent sidebar panel.
5. Fix "Duyệt tất cả" semantics (needs your answer on option a vs b above).
6. Header/summary scene-and-duration stats — pending your answer on question #5 above about data availability.

Answer the two open questions (approve-all semantics, and whether scene/duration stats are expected pre-finalize) before starting so you're not guessing mid-implementation. Regression-test the toggle behaviors (flag/approve un-toggling) and the shared-panel-targets-selection behavior specifically, since those are the parts most likely to have subtle bugs. Report back with commit hash(es) as usual.
